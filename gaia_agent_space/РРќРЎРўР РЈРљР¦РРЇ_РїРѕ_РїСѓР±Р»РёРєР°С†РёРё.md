# Как опубликовать агента для финального задания (Unit 4, бенчмарк GAIA)

Код готов и лежит в этой папке (`app.py`, `agent.py`, `tools.py`, `requirements.txt`). Дальше — шаги, которые нужно сделать вам самим в вашем аккаунте Hugging Face: я не могу входить под вашим аккаунтом, вписывать токены или публиковать что-либо от вашего имени.

## Что за агент

Это `smolagents.CodeAgent` — он пишет и исполняет код на Python, чтобы отвечать на вопросы. У него есть девять инструментов:

- **веб-поиск** (DuckDuckGo) — искать актуальную информацию в интернете, включая Википедию;
- **чтение веб-страниц** — открыть найденную ссылку и прочитать её содержимое;
- **скачивание приложенного файла** — если к вопросу GAIA приложен файл, агент может скачать его по `task_id`;
- **распознавание речи в аудио** (`transcribe_audio`) — для вопросов с приложенным `.mp3`/`.wav`, модель Whisper. Работает и через Groq, и через Hugging Face; при заданном `GROQ_API_KEY` идёт в Groq, а при его сбое откатывается на HF;
- **расшифровка видео YouTube** (`get_youtube_transcript`) — вытаскивает субтитры ролика по ссылке, без скачивания видео;
- **зрение** (`describe_image`) — отправляет приложенную картинку в vision-модель и получает ответ по изображению; нужно для вопросов вида «посмотри на позицию на картинке». Тоже с двумя путями: Groq и Hugging Face, с откатом;
- **чтение PDF** (`read_pdf`) — извлекает текст из PDF по ссылке или локальному пути, с поиском по подстроке. Отдельный инструмент нужен потому, что готовый `visit_webpage` разбирает любой ответ как HTML, и на PDF выдаёт бинарный мусор;
- **чтение текстового файла** (`read_text_file`) — читает локальный `.py`/`.txt`/`.json`. Нужен из-за устройства песочницы smolagents: встроенный интерпретатор запрещает `open`, поэтому прочитать скачанный файл кодом агент физически не может — без этого инструмента указание «прочитай текст файла» было невыполнимым;
- **Википедия напрямую** (`wikipedia`) — обращается к API Википедии, минуя поисковик. Нужен по двум причинам: DuckDuckGo на Spaces регулярно упирается в лимиты, а главное — в режиме `mode='tables'` инструмент отдаёт таблицы статьи, по которым можно посчитать строки (альбомы по годам, статистика, число атлетов по странам). В обычном текстовом пересказе таблицы теряются, а вопросы GAIA требуют именно подсчёта.

Плюс встроенный в smolagents интерпретатор Python, которому явно разрешено использовать `pandas`/`openpyxl` (для вложенных `.xlsx`/`.csv`), `re`, `json`, `datetime`, `statistics` и т.п. — это нужно, чтобы агент сам мог разобрать вложенные таблицы и файлы прямо в написанном им коде.

Список инструментов подобран не абстрактно, а по факту: я разобрал реальные 20 вопросов текущего учебного набора GAIA (публичный `GET /questions`, без токена) — среди них есть вопросы с `.mp3`, `.xlsx`, `.py`-файлами, картинками, ссылками на YouTube и научными статьями в PDF. Без соответствующих инструментов агент такие вопросы не решил бы в принципе, а не просто отвечал бы хуже.

Полный разбор с оценкой шансов по каждому вопросу — в файле `АНАЛИЗ_вопросов.md`. Готовых ответов там нет специально: смысл задания в том, чтобы отвечал агент.

**Про язык.** Требования к формату ответа в промпте намеренно даны по-английски, хотя все пояснения в коде русские: вопросы и эталонные ответы GAIA англоязычные, а сверка дословная — русскоязычная инструкция повышала риск получить «Санкт-Петербург» там, где сервер ждёт «Saint Petersburg».

**Честное предупреждение о лимитах:** зрение теперь есть, но это отдельная VLM-модель, и на шахматной позиции такие модели ошибаются часто — ответ может оказаться неверным, хотя попытка будет осмысленной. Расшифровка YouTube даёт только то, что *произнесено* в видео, а не то, что видно на экране (вопрос про подсчёт птиц в кадре так по-прежнему не решить — для этого нужен видео-VLM покадрово). 30%+ не гарантированы: результат зависит от конкретных вопросов и от того, насколько сильная модель доступна на вашем ключе. Набор инструментов покрывает все типы вопросов, которые есть в текущем наборе, но качество ответов — уже вопрос модели.

## Шаг 0 (рекомендую). Проверить агента локально, ничего не публикуя

В папке есть `test_local.py` — он берёт вопросы с публичного API и прогоняет агента у вас на машине, **не отправляя** ответы на сервер оценки. Это позволяет убедиться, что модель доступна и агент отвечает осмысленно, до того как выкладывать Space:

```bash
pip install -r requirements.txt
set HF_TOKEN=ваш_токен        # Windows (в PowerShell: $env:HF_TOKEN="...")
python test_normalize.py      # формат ответа: 28 проверок, без сети и токена
python test_wikipedia.py      # разбор таблиц Википедии: 13 проверок
python test_model_select.py   # выбор рабочей модели: 14 проверок
python test_audit_fixes.py    # регрессии по найденным аудитом дефектам: 29 проверок
python test_space_startup.py  # реальный запуск приложения в окружении Space: 25 проверок
python test_provider.py       # выбор провайдера (Groq/HF) и откаты: 21 проверка
python test_submit_local.py    # локальная отправка, докачка после обрыва: 17 проверок
python test_app_flow.py       # прогон и отправка на заглушках: 8 проверок
python test_local.py          # один вопрос
python test_local.py --count 3
python test_local.py --all    # все 20 вопросов, долго
```

Если на этом шаге всё разумно — переходите к публикации.

**Про формат ответа.** Сервер оценки сверяет ответы *дословно*, поэтому лишняя точка или префикс «FINAL ANSWER:» превращают верный по смыслу ответ в неверный формально. Одних инструкций в промпте тут мало — модели всё равно добавляют пояснения. Поэтому ответ дополнительно чистится кодом (`normalize_answer` в `agent.py`): срезаются служебные префиксы, markdown-выделение, обрамляющие кавычки, точка в конце, разделители тысяч. При этом намеренно не трогаются регистр, десятичные дроби, аббревиатуры вида `U.S.A.` и списки через запятую — там правка навредила бы. `test_normalize.py` проверяет и то, что нужное чистится, и то, что остальное не портится (28 проверок).

**Про независимый аудит.** После того как код был готов, я отдал его на придирчивый разбор отдельному ревьюеру — и он нашёл ещё один дефект, обнуляющий всё: в зависимостях стоял `gradio`, тогда как кнопка входа `gr.LoginButton()` требует `gradio[oauth]` (пакет `authlib` идёт только с этим extra). Приложение падало бы при создании интерфейса: сборка проходит, а вкладка App отдаёт ошибку и кнопки запуска нет. Мой собственный `test_app_flow.py` это пропускал, потому что подменял кнопку входа заглушкой — то есть проверял всё, кроме единственного места, которое ломается на Space.

Там же нашлись три дефекта нормализации: ответ-список уходил на сервер питоновским представлением `['broccoli', 'celery']` вместо `broccoli, celery`; правило снятия разделителей тысяч склеивало список номеров страниц `132,133,134` в одно число; значение в markdown-заборчике вырождалось в пустую строку и стоило лишнего полного прогона. Всё исправлено и закрыто регрессионными тестами в `test_audit_fixes.py` — по одному тесту на каждый дефект, чтобы повторное появление сразу всплыло.

И главное следствие: добавлен `test_space_startup.py`, который **действительно поднимает приложение** в окружении, похожем на Space (выставляет те же переменные окружения, ничего не подменяет заглушками) и проверяет, что интерфейс собрался и вход через HF включён. Именно отсутствие такого теста дважды пропустило ошибки, обнулявшие прогон. Тест проверен «от противного»: на прежней, сломанной версии зависимостей он падает — иначе от него не было бы толку. Попутно он поймал и собственную ошибку: `gradio` читает переменные окружения в момент импорта, поэтому выставлять их нужно до любых импортов.

**Про выбор модели.** Модель — самое хрупкое место всей конструкции: если она недоступна на вашем токене, агент не ответит ни на один вопрос. Поэтому она больше не задана одной жёсткой строкой: при старте агент перебирает несколько кандидатов и коротким запросом проверяет, какая реально отвечает. Первой берётся ваша `MODEL_ID`, если задана, затем модель по умолчанию из установленной версии smolagents (библиотека держит там актуальное), затем распространённые instruct-модели. Модель из примеров курса (`Qwen/Qwen2.5-Coder-32B-Instruct`) осталась последней в списке — она могла уже перестать обслуживаться. Если не ответит никто, вы увидите не загадочный сбой, а внятное сообщение со списком того, что именно не сработало, и ссылкой на https://huggingface.co/inference/models

**Про сбои.** Каждый вопрос агент пробует дважды: отвал провайдера инференса (таймаут, 503, лимит) — штатное дело, и терять из-за него вопрос целиком не хочется. Больше двух попыток нет специально: если модель падает стабильно, повторы только затянут прогон всех 20 вопросов.


## Если исчерпан лимит Hugging Face Inference API

Это происходит легко: бесплатный месячный лимит HF невелик, а один прогон
20 вопросов агентом — это десятки запросов к модели. Симптом однозначный:
код полностью рабочий, но агент не отвечает ни на один вопрос.

Агент умеет работать через **Groq** — он бесплатен без привязки карты и
покрывает все три нужные способности сразу: чат, распознавание речи (Whisper)
и зрение. Отдельные сервисы под каждую заводить не нужно.

1. Получите ключ на https://console.groq.com/keys (регистрация без карты).
2. Задайте его переменной окружения — и всё, больше ничего менять не надо:

```bash
set GROQ_API_KEY=ваш_ключ_groq     # Windows; в bash: export GROQ_API_KEY=...
set HF_TOKEN=ваш_токен_hf          # всё ещё нужен: для создания Space и входа
python test_local.py --count 3
python deploy.py --name gaia-agent
```

`deploy.py` сам пропишет `GROQ_API_KEY` в секреты Space.

**Что важно понимать про два ключа.** Они нужны для разного, и один другого не
заменяет: `HF_TOKEN` — чтобы создать Space и чтобы пользователи входили в
приложение (сервер оценки записывает результат на ваше имя), `GROQ_API_KEY` —
чтобы работала сама модель. Если задан только `GROQ_API_KEY`, публиковать Space
будет нечем; если только `HF_TOKEN` при исчерпанном лимите — Space поднимется,
но агент не ответит.

Когда заданы оба, приоритет у Groq: раз вы прописали его ключ, значит лимит HF
уже исчерпан, и пробовать HF первым — потеря времени на каждом вопросе. При
этом откат сохранён: если Groq вернёт ошибку на распознавании речи или зрении,
инструмент попробует HF, а не потеряет вопрос.

Модели Groq по умолчанию: `openai/gpt-oss-120b` для рассуждения,
`whisper-large-v3` для речи, `qwen/qwen3.6-27b` для зрения. Заменить можно
секретами `MODEL_ID` и `GROQ_VISION_MODEL_ID`.

## Быстрый путь: одна команда вместо шагов 1-3

Если не хочется кликать по веб-интерфейсу, есть `deploy.py` — он сам создаёт Space, загружает файлы и прописывает секрет `HF_TOKEN`:

```bash
pip install huggingface_hub
set HF_TOKEN=ваш_токен          # Windows; в bash: export HF_TOKEN=...
python deploy.py --name gaia-agent --dry-run   # сначала посмотреть план
python deploy.py --name gaia-agent             # выполнить
```

Токену нужны права **Write** (при создании токена выберите Write, а не Read) — иначе он не сможет создать Space.

Токен читается из переменной окружения на вашей машине и уходит только в API Hugging Face. Скрипт его не печатает и никуда не сохраняет — это сделано специально, чтобы значение секрета не попало ни в логи, ни в консоль. Я к нему доступа не имею и иметь не должен.

Скрипт можно запускать повторно — существующий Space он обновит, а не упадёт с ошибкой. Полезно, если будете править `agent.py` и переливать заново.

После этого сразу переходите к шагу 4 (дождаться сборки). Ниже — тот же процесс руками, если предпочитаете видеть каждый шаг.



## Если агент «ходит по кругу» и упирается в лимит шагов

Наблюдение с реального прогона: на вопросе о дискографии модель сделала девять
шагов из двенадцати, каждый раз формулируя новый поисковый запрос вместо того,
чтобы открыть уже найденную страницу. Причина оказалась не в модели.

**Описания инструментов были написаны по-русски.** Это единственный текст, по
которому модель решает, какой инструмент вызвать, — а вопросы GAIA английские и
рассуждает модель по-английски. На несовпадении языков выбор инструмента
деградирует, и модель возвращается к тому, что понимает лучше всего: обычному
`web_search`. Все описания инструментов и их параметров переведены на
английский; пояснения и комментарии в коде остались русскими — они для человека,
модель их не видит.

Вместе с этим добавлено прямое указание против циклов: не повторять уже
сделанный поиск и его переформулировки, а открывать найденное; для Википедии
вызывать `wikipedia`, а для подсчётов — `mode='tables'`; при двух неудачных
подходах давать лучший обоснованный ответ, а не пробовать третью вариацию той же
идеи. Лимит шагов поднят с 12 до 16, а переплановка стала реже (каждые 5 шагов
вместо 3) — частая переплановка сама подталкивала к новым поискам.

Отдельно про этот вопрос: дискография Mercedes Sosa — это таблица в Википедии,
и правильный путь к нему `wikipedia(query="Mercedes Sosa discography",
mode="tables")` с подсчётом строк по годам, а не поиск в DuckDuckGo. Теперь
описание инструмента говорит об этом прямо.

## Если Space создать нельзя (free-аккаунт без PRO)

Hugging Face закрыл бесплатным аккаунтам создание CPU-Basic Gradio Spaces:
при создании доступен только ZeroGPU, а перевод на CPU Basic требует PRO
(обсуждения на форуме HF: «New free accounts cannot create CPU Basic Gradio
Spaces», «Gradio SDK now marked as Paid»). То есть путь из официальной
инструкции курса бесплатному аккаунту просто недоступен — это не ваша ошибка
и не ошибка в коде.

**Space для получения сертификата не обязателен.** Эндпоинт `/submit` сервера
оценки не требует авторизации: он принимает обычный POST с полями `username`,
`agent_code` и списком ответов. OAuth в Space нужен был лишь чтобы надёжно
узнать ваш ник. Значит, агента можно прогнать локально и отправить ответы
напрямую — этим занимается `submit_local.py`.

```bash
set GROQ_API_KEY=ваш_ключ

# 1. Прогон. Ответы пишутся в answers.json после КАЖДОГО вопроса
python submit_local.py run --all

# 2. Посмотреть, что уйдёт на сервер
python submit_local.py submit --username ВАШ_НИК_НА_HF --dry-run

# 3. Отправить
python submit_local.py submit --username ВАШ_НИК_НА_HF \
    --agent-code https://github.com/KonstantinVCH/gaia-agent
```

Прогон и отправка разделены намеренно: 20 вопросов идут минуты, и терять их
из-за сетевой ошибки при отправке нельзя. Если прогон прервётся, повторный
запуск `run` доберёт только недостающие вопросы, а не начнёт заново.

**Про честность этого пути — прочитайте, это важно.** Требование курса про
публичный Space существует, чтобы код можно было проверить. Поэтому
`--agent-code` должен вести на публично доступный код — ваш репозиторий на
GitHub подходит. Отвечает по-прежнему агент, ответы нигде не подставляются
вручную. Но это отклонение от буквы инструкции: в лидерборде ссылка будет
вести на GitHub, а не на Space. Решение за вами — я обязан сказать об этом
прямо, а не выдать обход за штатный путь.

Чего я не знаю заранее: проверяет ли сервер оценки формат поля `agent_code`.
Если он потребует именно ссылку на Space, скрипт покажет ответ сервера
целиком, и ответы при этом останутся в `answers.json` — повторить отправку
можно будет без нового прогона.

## Шаг 1. Создать Space на Hugging Face

1. Зайдите на https://huggingface.co/new-space под своим аккаунтом.
2. **SDK**: выберите **Gradio**.
3. **Visibility**: **Public** (это обязательное требование задания — ссылка на код должна быть публичной для проверки).
4. Название — любое, например `gaia-agent`.
5. Нажмите **Create Space**.

(Альтернатива — сначала продублировать официальный шаблон `agents-course/Final_Assignment_Template` кнопкой "Duplicate this Space" на его странице, а затем в своей копии заменить файлы на файлы из этой папки. Результат тот же.)

## Шаг 2. Загрузить файлы

В интерфейсе своего нового Space откройте вкладку **Files**, и через **Add file → Upload files** загрузите пять файлов из этой папки:

- `app.py`
- `agent.py`
- `tools.py`
- `requirements.txt`
- `README.md` — **не пропускайте его**: в нём YAML-шапка, по которой Hugging Face понимает, что собирать Gradio-приложение из `app.py` и включить вход через HF (`hf_oauth: true`). Если Space создавался через веб-интерфейс, свой `README.md` там уже есть — замените его этим (или перенесите из моего YAML-шапку в свой).

(Файлы `test_*.py`, `deploy.py` и `.md`-документы загружать не нужно — они для локальной работы. `deploy.py` сам отбирает ровно эти пять файлов.)

Про версию Gradio: в шапке `README.md` закреплено `sdk_version: 6.25.0`. Официальный шаблон курса написан под Gradio 5, и напрашивалось закрепить пятую версию — но я это проверил, а не предположил: Gradio 6 сохранил именно тот механизм, на котором держится вход (автоподстановку `gr.OAuthProfile | None` в обработчик), и весь интерфейс на нём собирается. Поэтому пин указывает на версию, против которой код реально протестирован, а не морозит проект на стареющем Gradio 5, который Spaces однажды может перестать предлагать.

## Шаг 3. Добавить токен Hugging Face в секреты Space

Агенту нужен доступ к Hugging Face Inference API, чтобы вызывать LLM. Для этого:

1. В своём Space откройте **Settings → Variables and secrets**.
2. Добавьте новый **Secret**: имя `HF_TOKEN`, значение — ваш токен доступа Hugging Face.
   - Получить токен: https://huggingface.co/settings/tokens → **New token** → тип **Read** (или Fine-grained с доступом к Inference) достаточно.
3. При необходимости можно также добавить секреты:
   - `MODEL_ID` — заменить основную модель (по умолчанию `Qwen/Qwen2.5-Coder-32B-Instruct`);
   - `VISION_MODEL_ID` — заменить vision-модель (по умолчанию `Qwen/Qwen2.5-VL-72B-Instruct`).

   Обе модели по умолчанию я проверил через API Hugging Face — на момент подготовки кода они значатся как доступные (`status: live`) у провайдеров инференса. Но доступность зависит и от вашего тарифа, поэтому если получите ошибку доступа — переопределите модель этими секретами.

## Шаг 4. Дождаться сборки и открыть приложение

После загрузки файлов Space автоматически начнёт сборку (Building). Когда статус сменится на **Running**, откройте вкладку **App**.

## Шаг 5. Запустить и отправить

1. Нажмите кнопку входа (**Sign in with Hugging Face**) в самом приложении.
2. Нажмите **«Run Evaluation & Submit All Answers»**.
3. Агент последовательно пройдёт все 20 вопросов (это может занять несколько минут) и автоматически отправит ответы на сервер оценки.
4. Результат (процент правильных ответов) появится в текстовом поле статуса.

## Шаг 6. Если результат ≥ 30% — получить сертификат

Зайдите на страницу сертификата курса (раздел «Get Your Certificate Of Excellence» → «certificate page»), войдите через Hugging Face, укажите полное имя и нажмите **«Get My Certificate»**.

## Если что-то пошло не так

- **Ошибка модели / 429 / доступ запрещён** — значит выбранная модель недоступна на вашем токене/тарифе. Добавьте секрет `MODEL_ID` с другой моделью (например, `meta-llama/Llama-3.3-70B-Instruct` или любой другой, доступной вам через Inference Providers на Hugging Face).
- **Долгая сборка / ошибка зависимостей** — проверьте, что `requirements.txt` загружен и не был случайно изменён при загрузке.
- **Низкий результат** — это ожидаемо для базового агента; при желании можно улучшать `agent.py`/`tools.py` (добавить, например, инструмент для чтения таблиц/PDF, более сильную модель, дополнительные попытки на вопрос) — этим стоит заняться уже самостоятельно или вернуться ко мне за доработкой конкретных мест.
